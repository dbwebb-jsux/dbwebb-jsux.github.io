## HTML5 input typer

I och med introduktionen av HTML5 introducerades även ett antal nya [input typer](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/input). Dessa typer specificerar vilken sorts data som inputfältet kan ta som indata. Detta gör det möjligt att hindra användaren från att fylla i fel sorts data, men även att anpassa användargränssnittet till det data som användaren skall fylla i. Nedan finns en listning av 6 input typer och hur en mobila enhet anpassas för input typen. Inputfälten visas i Android emulatorns webbläsare.

Det helt vanliga text input fältet ger ett vanligt tangentbord och ingen klient validering av vilka värden som fylls i.

```html
<input type="text">
```

<Image src={inputText} alt="Input type text" class="input-img" />



Om man har ett fält där användaren ska ange ett tal som man kan räkna med, till exempel antal, kan man använda sig av `number`. Detta gör att tangentbordet på mobila enheter bytts ut mot ett numeriskt och att det inte går att fylla i annat än karaktärer relaterade till siffror.

Använd däremot **inte** `number` för siffror som inte är tal, som postnummer, telefonnummer, personnummer eller kortnummer. Ett postnummer som "379 79" innehåller ett mellanslag, ett postnummer kan börja med 0 och man ska aldrig räkna med det, och `number` ger dessutom upp- och nedpilar och ändrar värdet när man scrollar. Använd istället `type="text"` med `inputmode="numeric"` (som ger det numeriska tangentbordet på mobilen) och ett `pattern`:

```html
<input type="text" inputmode="numeric" pattern="[0-9]{3} ?[0-9]{2}" autocomplete="postal-code">
```

```html
<input type="number">
```

<Image src={inputNumber} alt="Input type number" class="input-img" />



Om användaren skall fylla i sin e-postadress kan det vara bra med ett input av typen `email`. Det underlättar för användaren när man skall använda @.

```html
<input type="email">
```

<Image src={inputEmail} alt="Input type email" class="input-img" />



Vid ifyllning av telefonnummer kan det vara fördelaktigt att använda input av typen `tel`. Där får användaren upp ett numeriskt tangentbord, som ser ut som det man använder när man skall ringa från en telefon.

```html
<input type="tel">
```

<Image src={inputTel} alt="Input type tel" class="input-img" />



När vi har datumfält finns input av typen `date`. Med `date` får användaren av en mobil enhet upp en datum väljare. På desktop skiljer det mellan de olika webbläsare, men Chrome och Firefox ger användaren möjlighet för att välja datum formaterat enligt användarens inställningar. Det värde som skickas med när vi skickar formuläret är alltid formaterat enligt 'YYYY-MM-DD'.

```html
<input type="date">
```

<Image src={inputDate} alt="Input type date" class="input-img" />



För fält där vi vill skriva in lösenord använder vi naturligtvis `password`.

```html
<input type="password">
```

## HTML5 validering av innehåll

En viktig del av att designa ett formulär är att ge återkoppling till användaren om hen har fyllt i ett värde som är korrekt för detta fältet. Vi såg ovan att input-typen kan ta oss en bit på vägen, men vad om vi vill validera användarens innehåll ytterligare? "HTML5 to the rescue". Som alltid har MDN en bra artikel om dessa möjligheter: [Client-side form validation](https://developer.mozilla.org/en-US/docs/Learn/Forms/Form_validation).

I HTML5 finns fyra olika attribut vi kan använda på våra formulärfält för att validera innehållet.

### required

Om vi vill att ett specifikt fält måste vara ifyllt kan vi använda `required` på följande sätt. Om fältet är tomt när vi skickar formuläret, får vi upp en varning om detta.

```html
<input type="text" required="required">
```



### minlength & maxlength

Som vi nästan kan räkna ut baserad på attributen kan vi här bestämma minimums och maximums längd för vårt innehåll. Om du använder dessa se till att det inte hindrar någon i att fylla data. Till exempel om man sätter får hårda krav på ett namn eller liknande.

```html
<input type="text" minlength="3" maxlength="8">
```


### min, max & step

Kan användas tillsammans med numeriska input-fält (number, date, time, range) för att begränsa värdena. Step anger vilket steg användaren kan ta mellan olika värden.

```html
<input type="number" min="0" max="1" step="0.1">
```


### pattern

Om man vill ta det ett steg längre kan man använda så kallade reguljära uttryck för att validera fältens innehåll. Till exempel om vi vill validera ett personnummer kan vi göra följande.

```html
<label for="zip">Postnummer (fem siffror, till exempel 379 79)</label>
<input type="text" id="zip" inputmode="numeric" pattern="[0-9]{3} ?[0-9]{2}">
```

Vi skriver formatet i synlig text vid fältet istället för i ett `placeholder`-attribut. En placeholder försvinner så fort användaren börjar skriva, och många tolkar den som att fältet redan är ifyllt. Det är en av rekommendationerna i artikeln [Website Forms Usability](https://www.nngroup.com/articles/web-form-design/) från kursmomentet.



### CSS-pseudoklasser

Ytterligare en fördel med form valideringen är att om fältet validerar får fältet pseudoklassen `:valid`. Om fältet inte validerar har det pseudoklassen `:invalid`. Problemet med `:invalid` är att den gäller direkt när sidan laddas, så alla tomma fält med `required` blir "felaktiga" innan användaren har hunnit skriva något. Därför finns pseudoklassen `:user-invalid`, som först börjar gälla när användaren har interagerat med fältet (till exempel lämnat det). Vi kan sedan använda den för att styla våra input fält. I nästa del av artikeln använder vi denna möjlighet.



## Styling av formulär

När vi designar formulärfält vill vi att de olika fälten ser likadana ut. Vi ska i denna del av övningen titta på hur vi kan designa formulärfält som är enhetligt designade i olika webbläsare. Hur vi lägger till genomtänkta förifyllda värden och hur vi tydligt visar för användaren vilket fält som är i fokus.

Vi börjar med den enhetliga stylingen. Vi börjar med att definiera klassen `.input` då kan vi använda klassen när vi vill ge styling till element. Vi vill som för knapparna ha ett mjukt utseende och rundar därför hörnen på samma sätt som för knapparna. Vi vill ha samma tunna ram runt knappen och vi vill ha samma typsnitt i formulärfälten som på resten av sidan. Vi vill även ha samma bredd på alla formulärfält trots de olika typer och vi specificerar bredden i `rem`. Vi ökar den inre marginalen (padding) så att fälten blir lättare att klicka på. Vi vill även ha ett avstånd mellan formulärfältet och sätter det som `margin-bottom`.

```css
/* forms.css */
.input {
  font-size: 1rem;
  line-height: 1.4;
  font-family: sans-serif;
  display: block;
  border: 1px solid #767676;
  border-radius: 0.2rem;
  padding: 0.6rem;
  width: 32rem;
  max-width: 100%;
  margin-bottom: 1rem;
}

.button {
  display: inline-block;
  font-size: 1rem;
  font-family: sans-serif;
  background-color: var(--text-color);
  color: var(--background-color);
  border: 0;
  border-radius: 0.2rem;
  padding: 0.6rem 1.2rem;
  text-decoration: none;
  cursor: pointer;
}
```

Reglerna `.input` och `.button` ovan ger fälten och knapparna (även "Beställ"-länken `<a class="button">` i varukorgen) ett enhetligt utseende. Färgerna `--text-color` och `--background-color` kommer från din `variables.css` från kmom02, byt ut dem mot egna värden om du har andra namn.

För att visa att ett fält är felaktigt använder vi `:user-invalid`. Vi får inte förlita oss på färg ensam (rött och grönt är svårt att skilja för många), så vi lägger även till en tjockare ram och en bakgrund, och i HTML:en skriver vi tydligt vilket format som gäller i en text vid fältet. Vi markerar inte "rätt" med grönt, det räcker att visa när något är fel.

```css
/* forms.css */
.input:user-invalid {
  border: 3px solid #b00020;
  background-color: #fdecea;
}

.input:focus-visible {
  outline: 3px solid #1a73e8;
  outline-offset: 2px;
}
```



## Hantera data med formData

När vi har fått till ett bra formulär vill vi även kunna använda datan från formuläret till något. I `order.html` lägger vi först till ett formulär, som i detta fallet enbart innehåller förnamn, e-post och en skicka beställningsknapp. Jag har i CSS-filen valt att dölja formuläret och först visa det när Stripe-betalningen gått igenom, det vill säga när `session.status == 'complete'`. Det gör vi med en klass `visible` som vi lägger till från JavaScript:

```css
/* forms.css */
.order-form {
  display: none;
}

.order-form.visible {
  display: block;
}
```

```html
<!-- order.html -->
<form id="order-form" class="order-form">
    <label for="firstname">Förnamn</label>
    <input class="input" type="text" name="firstname" id="firstname" autocomplete="given-name" required>

    <label for="email">E-post (hämtas från din betalning)</label>
    <input class="input" type="email" readonly name="email" id="email">

    <input type="submit" id="send-order" class="button" value="Skicka beställning">
</form>
```

Vi använder `readonly` och inte `disabled` på e-postfältet. Ett `disabled` fält tas **inte** med i `FormData`, så `formData.get("email")` skulle ge `null`. Ett `readonly` fält kan inte ändras av användaren men skickas med. Vi fyller i fältet med e-postadressen från Stripe-sessionen (`session.customer_email`) och visar formuläret när betalningen är genomförd. Det gör vi i `if (session.status == 'complete')`-grenen som vi skrev i [Integrera Stripe](/kunskap/integrera_stripe), istället för `console.log(session)`:

```javascript
// order.js
const orderForm = document.getElementById("order-form")

if (session.status == 'complete') {
  document.getElementById("email").value = session.customer_email
  orderForm.classList.add("visible")
}
```

Notera att `orderForm` hämtas på modulnivå och att `session` är den variabel på modulnivå som vi skapade i den andra övningen. I `order.js` skapar vi en `EventListener` för `submit`-eventet på vårt formulär.

```javascript
// order.js
orderForm.addEventListener("submit", handleSubmit)

async function handleSubmit(event) {
  event.preventDefault()

  const formData = new FormData(event.target)

  console.log(formData)
}
```

Vi kan nu komma åt de enskilda delar av `formData` objektet genom att använda `formData.get("email")` eller `formData.get("firstname")` och därigenom bygga upp ett `orderData`-objekt som vi kan skicka till Lager API:t för att skapa en ny order.

```javascript
// order.js
const orderData = {
    name: formData.get("firstname"),
    email: session.customer_email,
    payment_id: session.payment_id,
    api_key: auth.api_key,
}
```

`session` är objektet vi fick från `/stripe/session-status` och sparade i en variabel på modulnivå (`let session`) i [Integrera Stripe](/kunskap/integrera_stripe). Den måste ligga utanför `if`-blocket, annars kommer inte `handleSubmit` åt den. E-postadressen kan vi alltså läsa både från formuläret och direkt från `session`.

Jag har valt att lägga anropen mot API:t i en egen modul, `models/orders.js`. `createOrder` skickar en POST till `/orders` och `addOrderItem` en POST till `/order_items`. API:t svarar med ett objekt där själva ordern ligger under `data`, så det nya ordernumret är `result.data.id`.

```javascript
// models/orders.js
import auth from "./auth.js"

async function post(path, body) {
  const response = await fetch(`${auth.api_url}/${path}`, {
    body: JSON.stringify(body),
    headers: {
      'content-type': 'application/json'
    },
    method: "POST",
  })

  return await response.json()
}

const orders = {
  createOrder: (orderData) => post("orders", orderData),
  addOrderItem: (orderItemData) => post("order_items", orderItemData),
}

export default orders
```

När vi har skapat en ny order i Lager API:t får vi alltså tillbaka det nya objektet där `data.id` är ordens id, som vi sedan kan använda för att skapa `order_items` som läggs till den ordern vi precis skapat. Vi lägger det i `handleSubmit`, efter att vi har byggt `orderData`.

```javascript
// order.js
import orders from "../models/orders.js"

// i handleSubmit, efter att orderData är byggt
const cart = JSON.parse(localStorage.getItem("cart") || "{}")
const newOrder = await orders.createOrder(orderData)
const newOrderId = newOrder.data.id

for (let product in cart) {
    const orderItemData = {
        order_id: newOrderId,
        product_id: product,
        amount: cart[product],
        api_key: auth.api_key,
    }

    await orders.addOrderItem(orderItemData)
}
```

Efter att alla `order_items` är skapade ska varukorgen tömmas och räknaren från del 3 (siffran på varukorgsikonen) uppdateras. Om du bara gör `localStorage.removeItem("cart")` står räknaren kvar tills sidan laddas om. Låt därför `cart.js` exportera en funktion som både tömmer varukorgen och uppdaterar räknaren, och anropa den från `order.js`. Så här kan den se ut, anpassa efter hur du har byggt räknaren:

```javascript
// cart.js
function clearCart() {
  localStorage.removeItem("cart")
  updateCartCount() // din funktion som skriver ut räknaren
}

export { instantiateCartButtons, clearCart }
```
